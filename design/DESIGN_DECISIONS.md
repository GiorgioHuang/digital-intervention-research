| D-22 | How to word emergency access (break-glass) | **Call it "recording", not "gaining access"** | The permission engine never queries `break_glass_records`, so executing break-glass **grants nobody anything**, and the `expiresAt` in the record closes nothing when it arrives. | D-23 | Moderation decisions: which of the ten outcomes can go on screen | **Four real ones + one "record what you did elsewhere"; five stay off** | This is the most serious instance of "a recorded decision nobody reads" in this repository so far. **Nothing reads** `moderation_decisions`, and before this fix the three values `Hidden` / `Removed` / `Restored` of `post_state`, though written into the CHECK constraint, **were never written by any code either** — meaning that "remove content" closed the case as Actioned, told the moderator it was done, and left the post sitting in the community. The moderator, the reporter and the reported person would all three believe something had happened. **The fix**: the community feed only ever showed `Published`, so only the write side was missing — `Hide` / `Remove` / `Restore` now change the post's state in the same transaction, which makes those three real; `Dismiss` closes the case, and closing the case is its entire effect. **"Warn" is kept but rewritten**: it means "you spoke to them elsewhere, and this records that", the same shape as C15 "record an analysis run" and D-22 "record emergency access", and the screen says plainly that the platform sends nothing. **Off screen**: restrict features, suspend an account, disconnect, ban — the platform has no account restriction mechanism at all, and a button called "suspend account" would close the case, report success, and leave that person still posting. **Escalation stays off too**: there is no path from moderation to safety (E6 unimplemented), and recording an escalation would only move the case out of your hands without moving it into anyone else's. | D-24 | When reporting a post, who names the reported person | **The post does, not the reporter** | The same lesson as D-13: a permission named in the request is not a permission. | D-25 | Approval screens have only one exit, "agree" | **Add "say no" wherever the schema already has a refusal state** | Sweeping the whole database with the mechanical criterion "defined in a CHECK constraint but never written by any code" turned up the most serious one yet: **of the platform's eight approval commands, not one can refuse**. And five of those artefacts **already have refusal in their state vocabulary** — protocol versions, evidence decisions, analysis plans and research findings have `Rejected`, and evidence reviews have `Returned for Revision` — with no code path able to write them. **A decision screen with one exit is not a decision screen**: the only way for an approver to clear their queue is to approve everything in it, while the screen tells them "you can decide about this version". Separation of duties, exact versions, content hashes and confirmation dialogs were all built on top of a choice that never existed. **Landing**: migration 1753800000021 adds `refused_by_actor_id` / `refused_reason` / `refused_at` to those five tables, plus two CHECKs — the refuser may not be the submitter (the same rule as approval), and **no reason means no refusal**. At the command layer, refusal and approval **share the same permission key** (they are two ways of exercising the same authority, consistent with what C17's export decision already does), so since `finding.approve` is at the MFA tier, refusing a research finding requires MFA too — refusal is not the cheap half of a decision. The reason is mandatory, because someone whose work is refused has to be able to find out why. **Refusing an evidence decision writes no snapshot** — a snapshot is the immutable record of what an agreed decision rested on, and a refused decision has nothing anyone can cite afterwards. **Still missing**: the state vocabularies of dataset definitions, interpretation records and report versions have **no** refusal state, and adding one there means changing the vocabulary rather than just adding columns, so it is left to a separate ruling | Implementation-derived, 2026-08-05 |
| D-26 | You can get in but not out: leaving a community membership and a connection | **Add both exits; leaving must not depend on the permission that let you in** | The same mechanical criterion (defined in a CHECK, never written by any code) turned up a matching pair: `membership_state`'s `'Ended'` and `connection_state`'s `'Disconnected'` have been in the constraints from the start with **no code path able to write them**. So a community can be joined but not left — "participating in the community is entirely voluntary" was true only the first time; and a connection can be made but not ended — **the only exit was to block**, and blocking is a safety action about the other person, so an ordinary goodbye could only be dressed up as an accusation. That is a pressure the platform put on people, and it should not exist. **Both enforcement sides were already there** (the feed and posting both require Active membership; the message command refuses with `COMMUNICATION_BASIS_EXPIRED` when the basis is not Active) — only the write side was missing. **The key ruling**: `community.leave` **carries no consent precondition**. Joining is gated on `community-participation` consent; if leaving were gated the same way, the act of withdrawing that consent would trap the person inside the community that consent took them into — **an exit must never depend on the permission that let you in**. **Either side may disconnect**: requiring both to agree means the person who wants to leave has to wait for the other to nod, and that is not an exit. **The platform notifies nobody** — "X disconnected from you" announces someone's decision to leave, and being able to leave quietly is part of what makes it safe. Disconnecting sets that connection's conversations to `'Expired'` in the same transaction (a state whose copy, "the reason this conversation was possible has ended", was written long ago and was never reachable): leaving them Active would show "in progress" in the list while every send failed. **Neither is a deletion**, and the screens say so | Implementation-derived, 2026-08-06 |
| D-27 | What happens after something is confirmed as a safety event | **Add the event view, the action record and state progression; the wording must not let "closed" read as "the person is safe"** | `event_state` defaults to `'Open'` with **no code path able to change it**, no query listing safety events, and no screen that has ever shown one. The triage screen tells the safety reviewer "this has been converted to a safety event" — a sentence that reads like an escalation to something that will act on it — and **nothing acts on it**. This is the most serious record this platform holds (one person confirming another may be at risk), and it went into a table nobody could read and nobody could move. The read permission `safety-event.review` had been in the catalogue all along, with nothing to read. **Landing**: migration 1753800000022 adds an **append-only** `safety_event_timeline` (enforced by a trigger), with actions and state progression written onto the same timeline — otherwise "what happened" gets split in half with each half telling part of it; a correction is an appended entry and the original stays (the same rule as moderation decisions: a safety record that can be tidied up afterwards is not a record). The state machine lives in the command, and the interface offers only the steps the current state allows (otherwise it is another control that cannot be pressed). **Three pieces of wording are the substance here**: (1) the screen's first paragraph says **the platform itself does nothing** — it contacts nobody, restricts nothing and monitors nothing; every line here is a person writing down what they did; (2) choosing "resolved / closed" says plainly that **this does not mean the person is safe**, which is the most dangerous sentence this platform could produce; (3) beside the notes field it says **write what was done, not what was said** — the content of a call is a clinical record and does not belong here. **An empty state is also a judgement**: with no actions recorded the screen says "blank does not mean assessed", because a later reader cannot tell "no action needed" from "nobody looked", which makes "decided no action was needed" a real option. **An honest gap**: the design asks for "relationship to the intervention" to be shown, and the platform records it nowhere — the screen says plainly "this is not that nobody judged it, it is that the platform has nowhere to put that judgement" rather than quietly omitting it | Implementation-derived, 2026-08-06 |

| D-29 | A participant can write to a stranger but not to the family member they authorised themselves | **Ruling: make it a separate authorisable action on the relationship; implemented (2026-08-06)** | `conversation_threads.basis_type`'s `'AuthorisedRelationship'` had never been written: `createThread` accepted only a connection and hard-coded the basis.
