| D-10 | 参与者底部栏放几个目的地 | **四个：Home / Consent / Messages / Help** | 英文标签比中文长，五个槽位在真机宽度下装不下。实测（Chromium，root 18px，`--type-size-0`）：单个槽位 = (视口 − 18px 外内距 − 槽位间距) ÷ n，标签实际需要 53–77px。五槽在 320px 只给 56.8px，而 `Community` 需要 77px——390px 截图里它折成了 `Com/muni/ty`；四槽在 320px 给 72px，最宽的 `Messages`（当前项加粗时 67px）仍是整词单行。**让位的是 Community**：它是唯一被研究本身定义为可选的目的地，Doc 20 §33 要求常驻的是 Consent 与 Help，不是 Community；它仍在首页任务清单里，且 Home 恒在栏内，故任意屏到社区最多两下。同时补齐两条：底部栏在 200%/400% 放大时**换行成多行而非横滚或裁字**（I.2 已否决横滚导航），`main` 的下内距由 `--nav-primary-height` 按实测高度写入，避免两行时遮挡确认区。320/360/390/430px × root {18,24,32}px 六种组合已验证：无裁切、无横向溢出、触控高度均 ≥44px | D-3 的实施约束 / DESIGN_SYSTEM §G 视口矩阵 |
| D-11 | 数据集定义批准人与锁定人是否须为不同人 | **可以相同** | 与后端现状一致：`lockDatasetVersion` 只校验版本处于 `Quality Reviewed` 与 `dataset.lock` 权限，不比对定义的 `approved_by_actor_id`，因此无需改后端。锁定屏**明说这条规则**（`Locking is not barred by separation of duties…`），而不是靠沉默让批准过定义的人自己猜是否被允许——沉默会诱使人去点一个不确定的按钮。同时仍在每一行显示定义的批准人（M12 lockable 查询新增 `definitionApprovedByActorId`），并在批准人就是当前身份时标注「that is you, which is permitted here」：**允许不等于不可见**，链条即使不设卡也要可读。注意与之相邻的另一条规则不同：定义的**起草人不能批准该定义**（`created_by_actor_id <> approver`，DB 层强制），这条仍然成立，本裁定不触及 | RESEARCHER U2 |
| D-12 | PublicProfile 缺位时显示什么 | **显示参与者姓名** | 参与者之间不再出现内部标识：社区 feed 的作者、会话对象、连接对象一律显示 `participants.display_name`（M18 三个查询经新增的批量端口 `findDisplayNames` 解析，避免 feed 上 100 次单查）。**这修掉了一个已记录的真实缺陷**——原来界面直接渲染内部主键，等于把跨屏关联参与者的把手交给每一个读者。解析不到姓名时显示统一占位 `A community member`，**绝不回退到 ID**；占位对所有人相同，因此不能用来区分他们。**须知的代价**：Doc 20 §354 禁止把 ParticipantProfile 与 PublicProfile 合并，而 PublicProfile 目前尚未实现（B14 未实现），所以这不是边缘情况——**当前每一个对外显示的姓名都来自研究侧档案**，参与者无法按 §132 逐项选择自己被如何称呼。社区页因此明说「你发布的内容会带上参与者记录上的姓名；目前还没有可另选的社区用名」。B14 实现后应改为读 PublicProfile，本条即失效 | PARTICIPANT C2 |
| D-13 | 管理工作区能否列出参与者账号 | **必须能列出** | 新增权限 `participant.list-administrative`，只给 OrganisationAdministrator，**须声明 `platform-administration` 目的**，且**不设同意门**——这条只返回标识、姓名、账号状态，不含任何研究内容；若按 `study-participation` 同意来门控，撤回同意的人会从他仍然需要的账号管理里消失。受保护存在（ADR-050）不因此削弱：危险的形态是「拿调用方给的标识回答它是否存在」，而这里不接受任何标识，只在管理员已持有的范围内枚举。**组织范围一律取自请求上下文，绝不作为参数或查询串**——集成测试抓到过一个真实漏洞：当它还是参数时，引擎优先用资源上的组织，于是范围受限于 A 组织的管理员在 B 组织上下文里传 A 就能通过；现在权限判定与取数用同一个值，且调用方无法选择它。**已知缺口**：参与者与组织之间没有直接关联，只能经「账号 → 组织成员关系」连接，因此**没有平台账号的参与者不出现在列表里**，界面明说这不是完整名册。另外发现账号创建时并不写入组织成员关系（全库仅 3 条），列表因此会恒为空——已让演示种子在建账号时带上组织。**平台运维角色（SystemAdministrator）不获得此权限**：运维软件与看见研究里的人是两件事 | RESEARCHER U3 |
| D-14 | AI 消息草稿助手本阶段是否启用 | **暂不启用** | 代码里当前不存在任何 AI 起草入口（已核查：apps/web 无相关组件，权限目录无相关动作键），因此本裁定不需要改动实现，只作为「不要去建」的记录。若将来启用，仍须先回答被搁置的那个问题：是否向接收方披露该消息由 AI 起草——不披露会污染被研究的干预本身（参与者以为在读一个人写的话），这不是一个可以事后补的产品细节 | PARTICIPANT C5 |
| D-15 | 协助模式的身份模型 | **只读协助；消息向接收方披露** | 协助者**永远不代参与者操作**：不引入第二身份，`ActorReference` 与审计表都不改——因为在只读协助下，记录里「谁做了什么」从头到尾只有参与者一个人，本来就是真的。新增的是**对「谁在场」的诚实**。参与者自己开启与关闭（能被别人打开的模式，是披着「帮助」外衣的监视），常驻横幅写明「X 正在帮你」「他们能看到这个屏幕，包括你的消息」「X 不能替你按任何东西」。**协助者姓名只留在本机、绝不外传**——横幅需要它才能说人话，别人对它没有用途。**消息披露**：协助期间确认发出的消息，接收方会看到「发送时有人在协助对方，那个人能看到这段对话」。披露的理由不是作者身份（消息确实是参与者自己按的），而是**这段对话的听众比另一方以为的要大**，这是对方有权知道的。落地为 `messages.sent_with_assistance`（迁移 1753800000020）——**只存事实，不存协助者是谁**：把一个第三方的身份塞进他并不参与的对话里，既不必要也不正当 | PARTICIPANT C7 |
| D-16 | 生命故事的可见性与受众选择（B11）本阶段是否上屏 | **不上屏，等有读者** | 与 D-5 同一条规矩：`life_story.items.visibility` 现在写得进去，却**没有任何读取路径会去看它**。全仓库唯一读取生命故事条目的查询是 `getMyLifeStory`，而它是 `ownerOnly` 的——也就是说把一条内容改成 `Community` 或 `Connections`，实际的受众依然是零。此时给出「分享给社区」的控件，参与者会以为自己已经分享了而其实没有；这个方向的谎言和「以为私密其实公开」同样是谎言，只是伤害形态不同。`Selected People` 更明确：授权表 `life_story.access_grants` 根本没有任何命令能写入（只有撤回时的批量 revoke），所以「选定的人」是一个没有办法选人的选项。**当前实现**：生命故事屏只**显示**每条内容的可见性，不提供更改入口，且措辞按当前事实说（默认只有你能看到）。**解锁条件**：先实现一个尊重 `visibility` 与 `access_grants` 的非本人读取路径，以及一个写入 `access_grants` 的命令；届时 B11 才有东西可以诚实地控制 | 实现推导，2026-08-04 |
| D-17 | 参与者自填评估（B15）本阶段是否上屏 | **不上屏，缺两样东西** | 缺的第一样是权限：`assessment.record` 是 `{}`，不带任何 owner 作用域，只给 ResearchCoordinator——**参与者根本不能填自己的评估**，命令也不校验 `enrolmentId` 属于谁。缺的第二样更根本：**平台里没有量表题库**。`assessment_records.instrument` 与 `instrument_version` 是自由文本，没有任何表存放题目、选项、计分或版本（`research_design.research_questions` 是研究问题，不是问卷题目）。要把评估屏做出来，实现者就得编出题目内容——**量表题目是经过批准的研究材料，编一份出来会让研究收到的是一份没人批准过的工具产生的数据**，这比界面缺一屏严重得多。**连带后果**：首页「等你决定的事」区块刻意不列评估，尽管 `Scheduled` 与 `Available` 的记录确实存在；列一件参与者做不了的事，等于指一扇他打不开的门。**解锁条件**：（1）经批准的量表内容与版本化题库落库；（2）新增 owner 作用域的 `assessment.record-own`，资源归属由 enrolment 上的参与者推导，不接受调用方传入（D-13 的教训） | 实现推导，2026-08-04 |
| D-18 | 「切换使用者」是否连共享设备标记一起清掉 | **保留标记，其余全清** | §D.6 把切换使用者写成「完全清空 `sessionStorage`」，而共享设备标记正存在那里——照字面做，最保护人的那个设置会在陌生人坐下的那一刻消失。平板并没有因为使用者换了人就不再是公用的。**落地**：`endVisit()` 清空 `sessionStorage` 后把标记写回；关于人的一切（偏好、其他会话数据）不写回。**同类偏离**：环境访问口令仍留在 `localStorage`。它是原型环境的门钥匙而不是关于人的信息，清掉它会让整台公用平板从此进不来，除非重新拿到当初的邀请链接 | 实现推导，2026-08-05 |
| D-19 | 会话超时警告用粘性还是对话框 | **对话框** | §D.5 一边把「会话超时警告」列进粘性元素，一边规定粘性元素总高 ≤ 视口 25%，两条量出来是矛盾的：320×844 下这段话（标题＋为什么＋会丢什么＋倒计时＋两个按钮）占 665px，即 79%；xxl 下 790px。压进 211px 的唯一办法是删掉「你打了还没送出的内容会丢失」，而那正是这个对话框存在的理由。25% 上限管的是与内容并存、常驻抢占空间的框架元件；打断式警告在那一刻本身就是内容。**落地**：固定定位、贴视口上沿、`max-block-size` 加内部滚动（居中会在字号放大时把按钮同时挤出上下两端）。**不加遮罩、不声明 `aria-modal`**：在它后面点一下就是「人还在」，计时器因此重置、警告随即消失——那正是它要问的问题的答案 | 实现推导，2026-08-05 |
| D-20 | 超时警告是否沿用设计稿「已保存成草稿」的措辞 | **不沿用** | §E.11 的警告文案写着「你写的内容已经保存成草稿」。本平台没有任何地方保存草稿——这句话会在它即将被打破的那一刻做出承诺。**落地**：改说真话「你打了还没送出或保存的内容会丢失」，并由测试守住「saved as a draft」不得出现。**连带**：§E.11 另有一条「超时不得静默作废进行中的同意变更或评估」，在没有草稿机制之前只能靠「先警告、再登出」来满足，不能靠「已经存好了」来满足；真正的落地要等草稿功能 | 实现推导，2026-08-05 |

| D-33 | 同意文本改了，平台没有任何办法说这件事 | **补上写入方；由批准人记录，必须写明改了什么；已实施（2026-08-06）** | `consent_decisions.decision` 的 CHECK 里从建表起就有 `'ReConsentRequired'`，**权限引擎读它**（`engine.ts` 第 5 步：该范围下的一切当场拒绝），`assert.ts` 也为这个 outcome 备好了文案——一整套「你同意过的条款变了」的机制建好了、接通了、**没有任何一处能触发它**。于是同意文本可以改版，而每一位参与者继续挂在一份对已不存在的措辞的同意上，自己的同意屏还对他说「已同意」。**做法**：`consent.require-reconsent` 授给 ResearchApprover（改动条款的那一版正是他批的），`confirmationRequired`，**故意不是 ownerPermitted**——这是别人对你的同意做的唯一一件事，而且方向是收回而不是给予。**三条拒绝比那次写入更要紧**：（1）没有可被取代的同意（该范围是拒绝／撤回／未决）就拒绝——否则按下去什么都没变，却告诉按的人他做了事；（2）版本号与参与者已同意的相同就拒绝——那只会切断他的访问、又不给他任何新东西可读；（3）**必须写明改了什么**（迁移 `1753800000024` 加 `decision_note`）——不说改了什么就要人重新同意，那不是请求而是阻断：他无从判断被要求判断的东西，实际只剩「同意」一条路。参与者屏上用现在时说「已经停了，不是将要停」，并写明拒绝不牵连其他选择与他在研究中的位置 | 实现推导，2026-08-06 |
| D-34 | 平台最核心的那个模块（干预组合 M06）在产品里完全看不见 | **补上查询与两侧屏幕；证据分级照实说「没有」，不显示假分级；已实施（2026-08-06）** | M06 有六条路由——建干预、加版本、提交、批准、启用、按项目配置——**产品里没有任何一处调用它们**；而且 M06 **一个查询都没有**，所以哪怕直接打 API 建出来的干预，从那一刻起也再没人能看见。于是：批准人手上有两个决定，却无从得知有东西在等；提交了版本的研究者，查不到它后来怎么样了。对一个以「长者数字干预」为题的平台，干预恰好是唯一看不见的东西。**做法**：新增 `intervention.view`（研究者与批准人同持——他们是这次交换的两端，扣着列表等于让那两个决定无法抵达），列表按干预带出版本；研究者屏可建干预、加版本、提交，并**明说批准与启用不在这里**（提交人不能是批准人，服务端与数据库都拦）；批准人屏由列表驱动，每行只给它当前状态接受的那一个控件，启用前的确认写明**它顶掉哪一版**（唯一索引保证同一时刻只有一版在用，「启用」这个词把这层意思藏起来了）。**证据分级刻意不显示**：`evidence_status`（E0–E5）与 `evidence_direction` 两列**没有任何代码写过**，全库每一行都是默认值；把「E0 / Not Evaluated」印在干预旁边，会被读成有人评过它并给了最低档——在一个讲证据的平台上这是最误导的一种空白。屏上写明这两件事「平台里没有任何地方能记录，所以没有东西可显示；不是评过之后结果低」。**解除条件**：等证据评审的结论真的能写回干预（M10→M06 那条线），再把分级摆上去 | 实现推导，2026-08-06 |
